1. Resumen del caso y del proceso

La Parte 1 implementó en PostgreSQL un modelo relacional de los viajes de Uber y Lyft en Nueva York (enero–mayo 2026): 11 tablas, particionado mensual, control de calidad y feature engineering orientado a predecir demanda horaria.

En la Parte 2 se amplía ese caso hacia una arquitectura especializada complementaria (no sustituta): TimescaleDB (series temporales) + PostGIS (espacial). El objetivo es responder en tiempo casi real: ¿cuántos viajes se solicitarán en la próxima hora por zona y plataforma, y qué zonas presentan demanda anómala?

El proceso consistió en: (1) cargar los datos de la Parte 1 en un contenedor Docker, (2) añadir la capa espacial, (3) crear un hypertable de demanda, (4) crear un continuous aggregate, (5) activar compresión, y (6) ejecutar consultas de demostración temporales y espaciales. Todo es reproducible con scripts.

4. Selección de tecnología y comparación

Tecnología principal: TimescaleDB (extensión de PostgreSQL para series temporales).

Complemento espacial: PostGIS (aprovecha las coordenadas cargadas).

Qué problema resuelve: consultas de rango temporal y agregaciones sobre millones de observaciones con baja latencia, costosas con escaneo secuencial relacional.

Por qué se eligió: el dato es una serie temporal; aporta hypertables, compresión nativa y continuous aggregates, integrándose con el modelo relacional sin migración.

Ventaja demostrada: compresión de 162 MB → 14 MB (≈ 11,6×).

Limitaciones: la compresión de segmentos deshabilita ciertas escrituras directas sobre chunks comprimidos; menor paralelismo de escritura que soluciones distribuidas.

¿Por qué ambas y no reemplazar una por otra?

Por Polyglot Persistence: distintas tecnologías coexisten según las características de cada problema. PostgreSQL es la fuente de verdad transaccional (viajes, catálogos, lotes, reglas de calidad, integridad referencial). TimescaleDB y PostGIS optimizan el patrón de acceso analítico temporal–espacial que el relacional no resuelve eficientemente. Los datos fluyen de PostgreSQL hacia la capa especializada sin duplicar la lógica de negocio.

5. Modelo de datos especializado

Capa espacial (PostGIS)

ALTER TABLE core.zona_taxi
  ADD COLUMN geo GEOGRAPHY(POINT,4326);

UPDATE core.zona_taxi
SET geo = ST_SetSRID(ST_MakePoint(longitud, latitud), 4326)::geography
WHERE longitud IS NOT NULL AND latitud IS NOT NULL;

CREATE INDEX idx_zona_taxi_geo
  ON core.zona_taxi USING GIST (geo);

Hypertable (TimescaleDB)

CREATE TABLE analytics.demanda_serie (
  hora            TIMESTAMPTZ NOT NULL,
  zona_origen_id  SMALLINT    NOT NULL,
  plataforma_codigo VARCHAR(10) NOT NULL,
  viajes          BIGINT      NOT NULL
);

SELECT create_hypertable(
  'analytics.demanda_serie', 'hora',
  if_not_exists => TRUE);

Continuous aggregate

CREATE MATERIALIZED VIEW analytics.demanda_diaria
WITH (timescaledb.continuous) AS
SELECT time_bucket('1 day', hora) AS dia,
       zona_origen_id, plataforma_codigo,
       SUM(viajes) AS viajes, COUNT(*) AS n_horas
FROM analytics.demanda_serie
GROUP BY dia, zona_origen_id, plataforma_codigo
WITH NO DATA;

Compresión

ALTER TABLE analytics.demanda_serie SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'zona_origen_id, plataforma_codigo',
  timescaledb.compress_orderby   = 'hora');

SELECT add_compression_policy(
  'analytics.demanda_serie', INTERVAL '7 days');

7. Resultados reales de la implementación

Ejecutado sobre PostgreSQL 16 + TimescaleDB 2.31 + PostGIS 3.6 en contenedor Docker.

Caracterización (medido)

  • Viajes cargados: 4 999 931 — Uber 3 590 362 (71,81%), Lyft 1 409 569 (28,19%).
  • demanda_hora (relacional): 1 272 029 filas, 162 MB.
  • Hypertable demanda_serie: 1 272 029 filas, 22 chunks (todos comprimidos), 14 MB → factor ≈ 11,6×.

Consultas temporales

  • Hora pico global: 2026-02-07 19:00 → 3 163 viajes.
  • Día de mayor demanda: 2026-02-07 → 47 981 viajes.

Consultas espaciales

  • Top demanda en 2 km de Midtown Center: Times Sq 55 043, Midtown Center 55 014, Midtown South 45 399.
  • kNN desde JFK: Springfield Gardens South 2 514 m, Springfield Gardens North 3 012 m, Baisley Park 3 570 m.
  • Distancia centroides Midtown–JFK: 20 324 m (12,63 millas) frente a 17,56 millas de media en los 1 040 viajes reales con esa ruta.

8. Pasos para replicar

  1. Levantar el stack: docker compose up -d --build (carpeta deploy/).
  2. Ejecutar en orden: 01_schema.sql, 02_tables.sql, 03_data.sql, 06_zonas_geo.sql.
  3. Cargar los CSV de viaje e incidencia con \copy ... WITH (FORMAT csv, HEADER true, NULL '').
  4. Reconstruir analytics.demanda_hora.
  5. Ejecutar 07_timescale.sql (espacial + hypertable + continuous aggregate + compresión).
  6. Ejecutar 08_demo_queries.sql para reproducir los resultados.
  7. Compilar los PDFs (opcional): pdflatex informe_final.tex, modelo_nosql.tex, arquitectura.tex.
